# Week 3：订单数量上限与受控复现实验准备

日期：2026-11-03；负责：Xinyi Yang (xy2769)

## 可以汇报的结论

配置的 `BASE_MAX_ORDER_SIZE` 确实是 1000，但修改前，`AgentFactory` 没有将 `AGENT_PARAMS.max_order_size` 传入 agent；prompt 模板只要求 quantity 为股数，动态输出 schema 未声明 maximum，初始订单验证主要检查资源而没有检查这个配置上限。因此，“配置文件写了 1000”不等于“模型收到 1000 的限制”，更不等于“系统禁止超过 1000 的订单”。

本次使用当前本地代码实际构造请求，在高估/低估两个场景、四类角色、每类两个 agent、各两轮中捕获 32 份请求：均未出现明确的订单数量上限。另检查两组 10 月 13 日正式历史运行的 240 份已保存 prompt，未发现明确上限表述；三个 pilot 合计 48 份也未发现。历史扫描依赖已保存文本，不等于重新请求模型。当前目录没有 Git 元数据，不能把它直接称为作者论文所用原始版本。

## 本周实现

将参数接入 agent construction，并增加三种显式模式，默认仍保留 legacy，以免悄悄改变原实验。

| 模式 | Prompt 明确写上限 | 输出 schema 上限 | 初始订单入口硬校验 |
|---|---|---|---|
| legacy（默认） | 否 | 否 | 否；仍有原有资源检查 |
| prompt | 是 | 否 | 否；用于单独检验提示词影响 |
| enforced | 是 | 是 | 是，超限整单拒绝 |

- `max_order_size` 默认 1000；也支持指定其他正整数及按角色覆盖。用 37 做了配置传递检查，避免测试仅验证硬编码字符串 1000。
- 限制针对每笔订单，适用于自主提交的 buy/sell、market/limit；不是每轮总量，也不是 position limit。多笔各 1000 股订单仍可超过每轮总量 1000。
- 超限订单在资源冻结前被取消，原始数量保留，记录 `MAX_ORDER_SIZE_EXCEEDED`，不会静默截断到 1000。
- 系统强制平仓不纳入自主订单上限，避免阻止风险减仓；这两个 paper 场景不启用卖空。
- 原始角色 prompt 未重写；新限制以独立段落加入最终 user prompt。legacy 的原有 prompt 保持不变。
- schema 是否被真实供应商接受、GPT 实际服从程度仍需付费小规模验证；离线测试不回答模型行为问题。

## 离线验证与证据

1. 183 项针对性及回归测试通过，涵盖 schema 缓存隔离、角色参数覆盖、单/多股票 schema、买卖及市价/限价、1000/1001/100000 股、拒绝后账户与承诺不变，以及既有分红/价格/撮合/卖空/杠杆相关测试。
2. `synthetic_order_lifecycle.json` 保存两次完整模拟的逐单 ID、原始数量、成交数量、剩余量、状态和历史。确定性订单 fixture 绕过模型输出 schema，专门验证运行时防线：legacy 中 100000 股订单能够成交；enforced 中四笔超限订单被拒绝，四笔 1000 股订单正常成交。这不是 GPT 的实验结果。
3. 修复后共捕获 432 份请求，14 个完整模拟检查均通过；16 份首轮 legacy prompt 与修改前逐字相同。`rendered_requests.json` 与 `checks.json` 保存修复后三模式、两种 cap、两种起始价格的 prompt 检查，并包含高估/低估各 15 轮的固定分红重放。重放采用 Hold fixture，用来验证流程和真实账户分红，不用于估计市场行为。
4. 所有离线模拟脚本都阻断 socket 连接，替换 LLM service 为确定性 fixture；没有调用收费 API。

## Price measurement protocol

主指标：最近一次真实成交价，成交后的无成交轮次可 carry forward，并同时报告 stale/no-trade 标记。首次成交之前保持缺失；不能用初始价假装已成交价。若全程零成交，transaction-price convergence 不可估计，不应把它记为已观测到的收敛或零修正。

辅助指标：本轮成交价、轮成交量、同期撮合后 best bid/ask、双边存在时的 midpoint、simulator recorded price。初始价格和 fallback 价格应单独说明。估值分析区分 reported valuation 和可执行报价；accepted-order 分析与 proposed-order 分析不能混为同一统计口径。

## 下一步真实 GPT 验证（未运行）

先做 2 轮小规模接口兼容性检查，核对最终 messages、response schema、返回结果、订单拒绝日志和实际费用。模式不同会改变实验处理条件，应在 run manifest 中记录，不能覆盖或重新命名旧结果。

建议正式设计为高估/低估 × 三个固定 dividend paths（seeds 42/43/44）× 三种 size modes，共 18 个 15 轮 runs，名义上 2160 次 agent decisions，重试可能增加 API 请求数。计划保存于 `planned_matched_batch_NOT_RUN.json`，仅是配置文件，不会自动执行。先预算批准再启动；不是当前已经完成的实验。

- 固定模型快照、endpoint、温度、信息模式、角色 prompt、资金、路径和并发设置；记录源文件哈希与最终请求。
- 同一 dividend path 的三个处理组做配对；mode 的差异分别是 prompt 约束以及 schema+运行时校验的联合约束，不应把后者解释为纯运行时效应。
- 先增加同配置重复作为 noise-floor pilot；固定 seed/temperature 不保证 GPT 确定性。
- **相同 order seed 不等于相同订单序列**：订单集合/数量不同会改变 shuffle 结果；agent decision-order 当前还使用全局随机流。严格顺序匹配与 untreated-agent 输出重放尚未实现，现有方案只保证指定的 dividend path 和相关配置可核对。
- 以 run 为独立统计单位；三个 path 的初始批次是探索性结果，不足以宣称系统性风险或稳健的群体层面结论。

## 报告措辞建议（English）

The configured maximum order size was 1,000 shares, but our audit found that the parameter was not propagated into the rendered prompts or enforced by the original order-admission path in the inspected local code. Therefore, oversized orders cannot be interpreted simply as violations of an instruction received by the model. We implemented explicit legacy, prompt-only, and enforced modes, retaining the legacy default for comparison. Offline request capture and synthetic matching tests verify parameter propagation and rejection before resource commitment. Live-model compliance, provider schema compatibility, and causal market effects remain untested.

## 给 TA 的口头解释

这周我把上次提到的 max order size 往下追了一层。配置确实是 1000，但是原来的代码没有把它传进 agent 的 prompt，schema 和订单入口也没有真正执行这个上限。所以之前看到超大订单，不能直接说 GPT 不遵守规则，因为它可能根本没收到这个规则。我现在把它拆成 legacy、prompt-only 和 enforced 三种模式，并用离线完整模拟验证：超限订单会在冻结资金前被拒绝，正常 1000 股订单还能成交。下一步才是付费 GPT 小试跑，看看模型在收到限制后实际如何反应。这次没有用真实模型，所以我不会把这些工程测试当成新的市场实验结论。
