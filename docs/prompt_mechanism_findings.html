01 / FINDINGS

Three findings from the mechanism probes

The findings sit at three different layers: prompt instructions, simulator implementation, and model response stability. They should not be collapsed into one explanation.

Prompt hierarchy

Liquidity provision must be explicit

Loose market-maker wording was overridden by the agents' directional belief that the asset was overpriced. Making two-sided quoting mandatory changed the targeted behavior.

0/6 → 6/6 market makers quoting both bid and ask
Implementation gap

The declared order cap is inert

The scenario declares a 1,000-share maximum, but that value is neither shown to the LLM nor enforced in the live order path. Valid inventory was enough for oversized asks to be accepted.

100× largest accepted order relative to declared cap
Response stability

Fixed settings are not fixed outputs

Byte-identical non-market-maker prompts produced different actions and valuations. A single prompt comparison is therefore not a matched causal experiment.

Buy · Sell · Hold observed from the same rendered prompt

Mandatory two-sided system prompt — exact text 
You are a professional market maker whose mandatory role is to provide two-sided liquidity.

Your profit comes from capturing the spread between bid and ask prices, not from taking a directional position.

Short selling is NOT allowed. You can only sell shares you already own.

Mandatory quoting rule:
- In every round, submit at least one LIMIT buy order and at least one LIMIT sell order whenever your available cash and owned shares permit.
- This two-sided quoting requirement overrides your directional valuation view.
- Place buy orders 1-3% below the current market price and sell orders 1-3% above the current market price.
- Use a total spread of approximately 2-6% and never place the sell quote more than 10% above the buy quote.
- Do not use market orders.

Manage order quantities so that they remain within available cash and owned inventory. If both sides are feasible, a one-sided decision or Hold is not permitted.
03 / ORDER CAP

Declared in configuration, absent at runtime

The key issue is not that an agent disobeyed a visible 1,000-share instruction. The agent never received that instruction, and the simulator did not enforce it after generation.

Scenario max_order_size = 1000

Declared in src/scenarios/base.py:290,358.

Prompt construction Value not inserted

The user template only requests a positive quantity; no maximum is rendered.

Response schema Only quantity > 0

agents_api.py:24,30 checks positivity, not the scenario cap.

Runtime validation Cash / inventory only

A large sell is accepted when the agent owns enough shares.

Observed output 100,000-share asks

Ten oversized market-maker asks were accepted across three earliest-public repeats.

Interpretation

This is a configuration-to-runtime plumbing defect. It creates ambiguity between running the repository as written and running the experiment as its declared parameters imply.

Accepted size is not traded volume

What “stochastic” means here

temperature=0 and seed=42 reduce variation, but they did not guarantee response-level determinism for this API/model combination.

Research consequence

In a one-run A/B comparison, the measured difference contains both the market-maker prompt effect and unrelated response variation from agents whose prompts were never changed.

observed A–B difference = prompt effect + untreated-agent variation

Concrete example: in Repeat 1, Agent 2 chose Hold in the Current arm and the market had no trade. Under the Earliest-public arm, the same Agent 2 prompt instead produced a 1,000-share Buy and one trade. Comparing only these two runs could wrongly attribute the trade to the market-maker prompt, even though the initiating buy came from an untreated Optimistic agent.

05 / FILLS

Fully filled, partially filled, or unfilled?

The engine supports partial fills, but the nine probe runs did not produce any. In this audit, the LLM happened to generate 1,000-share executable orders on both sides, so each trade fully consumed one buy leg and one sell leg.

Matching mechanics

actual vs. hypothetical

Your intuition — corrected precisely

In the high-price market, asks greatly outnumber bids. When a crossing buy arrives, it matches the lowest-priced sell order first, with price-time priority—not “the smaller buy order.”

Why the 100,000-share asks were not partial

The observed 1,000-share buys reached lower-priced 1,000-share asks first. The oversized asks were accepted into the system but received zero execution, so their status was unfilled rather than partially filled.

Where did the 1,000-share buy size come from?

It was generated, not enforced

None of the three prompt arms received the numeric max_order_size=1000 value. The shared user prompt only says “quantity: number of shares,” and the response schema only requires a positive integer. Therefore, a 1,000-share output is not evidence that the configured cap worked.

Earliest-public · Repeat 1

Agent ID 2 (Optimistic) independently generated a 1,000-share market buy. It was not a market-maker order.

Earliest-public · Repeat 2

Agent ID 2 generated another 1,000-share market buy, and market maker ID 5 separately generated a 1,000-share limit bid.

Earliest-public · Repeat 3

No buy order was generated, so none of the accepted asks traded.

The exact reason the model repeatedly selected 1,000 cannot be identified from the code: it may be a learned round-number heuristic or a conservative choice relative to the displayed cash and inventory. The logs prove that the number came from the LLM response; they do not prove why the model preferred it.

06 / CLAIMS

What we can say now

Separating the claims keeps the replication result scientifically defensible.

Supported

  • The $56 state creates strongly one-sided sell pressure under the current prompt.
  • Explicit two-sided priority reliably restores market-maker bids.
  • The configured 1,000-share order cap is not enforced by the live path.
  • Fixed seed and temperature do not produce identical LLM decisions.
  • No partial fill occurred in the nine one-round probes.

Not yet supported

  • That AI herding causes a transaction-driven market crash.
  • That prompt wording alone caused the observed differences in total trade count.
  • That oversized accepted orders necessarily created executed volume.
  • That the current public repository exactly matches the code used for the paper's figures.
